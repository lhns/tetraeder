# 0059. Adaptive compute tier: decode admits a share of CPU misses into VRAM slots

Status: Proposed (2026-11-12, Phase 2 exit, ADR 0045 point 1)

## Context

On Qwen3-235B-A22B Q4_K_M (RTX 3090, 24 threads, `bench/results/20261112a`) llama.cpp's expert cache (`--moe-cache-mib 10458 --moe-cache-cpu-share 0.95`) decodes 1.35x to 1.54x faster than the builder with the same VRAM bytes. Its decode log: 35% of expert lookups hit VRAM, 92% of misses run on the CPU, the rest (about 37 experts, 400 MB per token) are uploaded into an LRU cache. The builder's compute tier is a static hot set: `refresh_hot_set` pins the top experts after the first prefill and `plan_cpu` never admits, so every other expert runs on the CPU. The replay puts the builder's decode VRAM pair share at 0.178 (`bench/results/20261110c/replay-235b.json`), and decode is CPU-bound (406 to 465 ms of CPU-heavy compute per token).

Hypothesis: raising the decode VRAM share toward llama.cpp's closes most of the gap. Estimates, not measured per expert: one CPU expert costs about 0.75 ms on that box (CPU compute per token over CPU experts per token); one synchronous upload of about 11 MB about 1 to 2 ms (pageable PCIe copy plus a host copy), so an admission pays when the expert is hit at least twice while resident (llama.cpp gets about 7 hits per upload).

## Decision

1. **Switch.** `LoadOptions::admit_share: Option<f64>`, off (`None`) by default. Only with `MissPolicy::Cpu`. Harness: `TETRAEDER_EXIT_ADMIT_SHARE`, recorded in the exit JSON `options.admit_share`.
2. **Policy** (`tetraeder_memory::slots::AdmitPolicy`, pure, shared with the replay): per MoE layer an integer credit that every compute-tier miss of a decode step (one token) raises by `share`; while the credit is at least one, the miss is admitted and the credit drops by one. Share `1/k` admits every k-th miss of a layer, deterministically. A miss that cannot be admitted keeps one admission due, no more, so a blocked step never causes a burst.
3. **Victims.** LRU among unpinned compute slots, never a pinned expert and never an expert this layer step computes from the compute tier or admitted already (`LayerSlots::lookup_except`). With the switch on, the hot set is the initial contents and is unpinned once resident (at every refresh), so the compute tier is LRU seeded by the hot set. Without that every slot is pinned and nothing could be admitted.
4. **Timing: CPU now, GPU from the next use.** An admitted expert is uploaded from its RAM slot after its CPU chunk is staged (the bytes are known to be there; under overlap after the layer's reads landed). So any miss can be admitted, also one read from disk in the same step, not only one already in RAM when the layer is planned: under prefetch and overlap a RAM slot at plan time may still be in flight. Its pairs still run in this step's CPU group. The step's groups are those of the switch off, so parity is unchanged: bitwise on the CPU backend, the existing tolerance on a GPU. Same-step GPU compute is deferred: it saves one CPU expert per admission but needs the upload before the plan, which under prefetch and overlap is before the bytes are known to be in RAM.
5. **Upload.** Synchronous on the main thread (`read_slot`, `write_slot`), before the next segment; it is not hidden behind compute. Its time goes to `tetraeder.expert.load.duration` (tier vram, source ram) and to `IoCounters::admit_time` (exit JSON `decode_io.admit_ms_per_token`). An async copy needs a pinned RAM tier and a `ggml_backend_tensor_set_async` binding (ggml-sys); it is the next step if the box shows the upload time matters.
6. **Metrics (Rule 6).** No new share metric: an admitted expert still counts once as `cpu` in `tetraeder.expert.cache.requests`, and its later uses count as vram `hit`. New: `tetraeder.expert.admitted` (experts, by layer) and `tetraeder.expert.admitted.bytes` (upload bytes), plus `tetraeder.tier.read.bytes` (tier ram) as for other uploads. The "Expert cache hit rate" panel gets an admissions-per-lookup series; alert `TetraederAdmissionsWithoutHits` fires when VRAM hits per admission stay below 2 for 15 minutes (by the estimates above, uploads then cost more than they save; recalibrate from `admit_ms_per_token` after the first paired run). `IoCounters` gains `admitted` and `admitted_bytes`; admissions also count in `uploads`.
7. **Bench.** Stages `main-overlap-adapt` and `main-overlap-adapt-repeat` (B1 `STAGES` only): `main-overlap` plus `TETRAEDER_EXIT_ADMIT_SHARE=0.1`, paired with `main-overlap` on the same box. Other shares through `VARIANTS`.

## Consequences

- Decode uploads again under `MissPolicy::Cpu` when the switch is on; with it off nothing changes (the flag-off tests stay as they are).
- The upload adds up to `share x misses x 1 to 2 ms` per token on the main thread. At 0.1 and about 600 misses per token that is 60 to 120 ms, more than the CPU time it saves in the step itself; it only pays through later hits. The paired run decides; if uploads dominate, the async copy comes next.
- The routing replay (ADR 0050) does not model admissions; a replay VRAM policy can reuse `AdmitPolicy`. A trace recorded with the switch on still shows the routing, not the tier.
- Prefill (more than one token) never admits, so a long prompt cannot flush the tier.

Admission works as designed: decode VRAM pair share 0.165 to 0.372 (the replay's `lru` gives 0.433, llama.cpp's cache 0.353), CPU pairs per token 628 to 473. But compute fell only 115.7 to 105.4 ms per token while the synchronous uploads cost 174 to 208 ms (about 530 MB per token, 2,981 admissions per run, no fall over the four windows). Without the upload time the step would be 188.5 and 194.6 ms against 201.9 and 200.6, a ceiling of 1.03x to 1.07x. ## Addendum 2026-11-12b: where the upload time goes, and async admission

This answers point 5's "next step" for the EPYC 7642 hosts, where `20261112a` measured about the same CPU core time per routed CPU pair for both engines (ours 17.8 and 20.8 core-ms at 628 CPU pairs per token, the cache's 16.9 and 17.4 at about 453), so the CPU pair count would set the decode rate there (628 / 453 = 1.39 against the measured 1.35x to 1.54x). `20261112c` showed admission does cut the pairs (628 to 473) but paid 208 ms per token for it: 46.6 admissions of 11.43 MB per token, 4.47 ms each, 2.56 GB/s.

**Our upload, from code.** `Streamer::admit` per expert: `read_slot` allocates a `Vec` of 11.4 MB and, per slab, `get_bytes` allocates a zeroed `Vec` and copies the RAM slot into it (`ggml_backend_tensor_get` on a CPU buffer is a `memcpy`), then appends it to the first: two host passes over freshly allocated pages, so about 5,600 page faults per expert. `write_slot` then calls `set_bytes` three times; the CUDA buffer's `set_tensor` is `cudaMemcpyAsync` on `cudaStreamPerThread` from pageable memory (the driver copies it once more into its own staging buffer, a third host pass) followed by `cudaStreamSynchronize`, so no slab's DMA overlaps the next slab's host work. All of it on the main thread, between a layer's planning and its next segment, while the threadpool's workers spin (`pool_pause` was off; the adapt runs used about 10 core-seconds per token against 5). How the 4.47 ms splits between faults, the two copies, the staging copy and the syncs cannot be read from code; the box stages below separate the host side from the transfer.

**llama.cpp's upload, from source** (b12274, `src/llama-moe-cache.cpp`, `impl::copy`): per layer, in the callback that copies the slot map, after one `ggml_backend_synchronize` for the routing ids, every miss to upload is one `ggml_backend_tensor_set_async(backend, bank, w->data + expert * size, ...)` (consecutive experts into consecutive slots merged) on the compute backend's own stream, straight from the model's host weight; no host copy, no sync per expert (the next layer's callback syncs). The source is pageable in the measured runs: `scripts/llamacpp_cache.sh` loads with `-lm auto` (mmap), and the loader avoids the pinned host buffer type under mmap (`llama-model-loader.cpp`, "avoid using a host buffer when using mmap"); only `-lm none` or `dio` would put CPU experts in `CUDA_Host` memory (`make_cpu_buft_list`). So its enqueue still blocks for the driver's staging copy (one host pass), and its uploads are on the critical path too, but at one host pass per expert instead of our three plus faults and per-slab syncs. `ggml_backend_sched_prefetch_inputs` is a different matter (the CPU split's inputs, ADR 0064) and not needed here.

**Decision.** `LoadOptions::admit_upload` picks how an admitted expert reaches its compute slot; the default stays the synchronous mode, `admit_share` stays off.

1. `Sync` (default): the copy goes straight from the RAM slot into the compute slot (`Tensor::copy_to`, `ggml_backend_tensor_set` from the host tensor's memory): no `Vec`, no faults, one staging pass by the driver and its sync per slab. Still on the main thread.
2. `Async`: a pinned staging ring of 8 experts' bytes in the GPU's host buffer type (`ggml_backend_dev_host_buffer_type`, `cudaMallocHost`; plain host memory where there is none, e.g. the CPU backend) and a second backend instance of the primary GPU, whose own CUDA stream (`ggml_backend_cuda_context::stream()`, created per instance, non-blocking) carries the copies, so they overlap the compute stream and the next segment's syncs do not wait for them. Per expert the main thread copies the RAM slot into a ring entry (one host pass, no faults: the ring is allocated and touched once) and enqueues `ggml_backend_tensor_set_async` from it (true DMA from pinned memory). A ring entry is reused only after the upload stream was synchronized; with 8 entries and DMA faster than the host copy, the wrap finds the stream idle. The RAM slot can be refilled right after the host copy, so no RAM-tier pinning is needed. Pinning the RAM tier itself (83 GB on the 235B box) would remove the host copy too, but page-locks and commits the whole tier at load, against ADR 0035's lazy commit and the huge page advice; a later step if the box shows the host copy matters.
3. **Barrier.** The compute table marks an admitted expert resident at admission, as before, so cache counters and LRU order are the same in both modes. Its slot is only read from the layer's next plan on: `plan_cpu`, `plan` and `make_resident` of a layer with uploads in flight (and `refresh_hot_set` for all layers) first synchronize the upload stream; dropping the uploader synchronizes it too. No ggml event: the pin has no event query, and a stream sync gives the same guarantee. The wait is normally zero (the layer's next use is a token later) and is counted (`IoCounters::admit_wait`). An admitted expert still runs on the CPU in its step, so parity is unchanged.
4. **Threadpool.** `admit` pauses the CPU threadpool (`Backend::pause_cpu_pool`, ADR 0061) before its first blocking copy of a layer step, in both modes, whether or not `pool_pause` is set: the workers would otherwise spin through the copies.
5. **Metrics (Rule 6).** No new instrument. Per admission: `tetraeder.expert.admitted(.bytes)`, `tetraeder.tier.read.bytes` (ram) and `tetraeder.tier.transfer.bytes` (ram to vram, purpose admission) as before; `tetraeder.tier.transfer.duration` and `tetraeder.expert.load.duration` get the main thread's time in `Sync` and none (transfer) or the host part (load) in `Async`, where the DMA time is not observed. `IoCounters` gains `admit_wait` beside `admit_time` (now the main thread's copy and enqueue time). The upload-wait histogram is not added: the wait is expected to be zero and the counter shows if not.
6. **Tests.** A test-only `Deferred` mode holds every copy until the barrier and poisons the destination slot meanwhile (`0xff` bytes, a NaN scale in every K-quant block), so any read before the barrier changes the logits; the `admit.rs` parity tests run in all three modes and must stay bitwise equal on the CPU backend, with equal cache counters across modes. A property test checks the ring never hands out an entry with a copy in flight.

**What only a box can verify.** That the second instance's stream overlaps the compute stream, that `cudaMallocHost` of the ring succeeds (else it falls back to pageable host memory, logged), the host copy's cost per expert and the barrier's wait. Stages: `main-overlap-adapt` (now `Sync` without the `Vec`) and `main-overlap-adapt-async` at shares 0.05 and 0.1, each with a repeat, paired with `main-overlap` on one box, preferably an EPYC 7642 host. The exit JSON needs `admit_upload` in `options` and `admit_wait_ms_per_token` in `decode_io`.
