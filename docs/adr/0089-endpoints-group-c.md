# 0089. Endpoints of llama-server (parity group C)

Status: Accepted (2026-11-23, under ADR 0083); item 5 in part superseded by ADR 0093 (`endpoint_slots` true). After M2. Matrix: [docs/notes/llamacpp-parity.md](../notes/llamacpp-parity.md). Tree node `serving-parity-endpoints`.

## Context

ADR 0083 asks that a request that works against llama-server at the pin (b12426) works against `tetraeder serve` on the same GGUF. Group C is the routes: health, metrics, props, tokenize, detokenize, apply-template, native completion, unprefixed aliases, Responses, infill and API keys. The pinned `tools/server` fixes routes, bodies, status codes and the auth rule; where the source and the first brief differ, the source wins.

## Decision

1. **Routes and aliases.** `/health` and `/v1/health`; `/props`; `/metrics`; `/tokenize`, `/detokenize`, `/apply-template`; native `/completion` and `/completions` (the same handler, as llama-server); `/infill`; `/v1/responses` and `/responses`; `/models`, `/chat/completions` next to their `/v1` forms. `/embeddings` and the `input_tokens` routes are not in this change (group D and open item).
2. **Errors.** Routes llama-server has natively answer with its error object `{"error": {"code", "message", "type"}}` (`format_error_response`: 400 `invalid_request_error`, 501 `not_supported_error`, 503 `unavailable_error`). The existing `/v1` routes keep their OpenAI body.
3. **API keys.** `--api-key` (comma separated, also `LLAMA_API_KEY`) and `--api-key-file` (one per line, `#` comments) as llama-server. A middleware in front of the whole router (so an unknown path is also 401) reads `Authorization` and, when that is empty, `X-Api-Key`; a `Bearer ` prefix is optional. Only `/health` and `/v1/health` are public; `/models` is not. 401 body `{"error": {"message": "Invalid API Key", "type": "authentication_error", "code": 401}}`.
4. **`/metrics`** is behind `--metrics` and 501 without it (llama-server's answer), Prometheus text with llama-server's names from gateway counters: `llamacpp:prompt_tokens_total`, `prompt_tokens_cached_total`, `prompt_seconds_total`, `tokens_predicted_total`, `tokens_predicted_seconds_total`, `n_tokens_max`, `prompt_tokens_seconds` and `predicted_tokens_seconds` (averaged over the window between two scrapes, as there), `requests_processing`, `requests_deferred`. Not exported because the gateway has no such number: `n_decode_total`, `n_busy_slots_per_decode` and the `spec_decode_*` family. The OTel metrics are unchanged.
5. **`/props`** returns what is true here: `default_generation_settings` (`params`, `n_ctx`), `total_slots`, `model_alias`, `model_path`, `chat_template`, `bos_token`, `eos_token`, `build_info`, `endpoint_metrics`, and the constant fields `endpoint_slots` false, `endpoint_props` false, `modalities`, `is_sleeping` false. `POST /props` is 501 without `--props`, as there; there is no `--props` flag because no property can be changed.
6. **Token routes** use the engine's tokenizer (the one DRY and grammars use): `Engine::tokenize_with(add_special, parse_special)`. `/tokenize` takes `content` (string or mixed array), `add_special` (default false), `parse_special` (default true), `with_pieces`; `/detokenize` concatenates the vocabulary pieces. The native prompt is tokenized with `add_special` true, as llama-server does; token-array prompts go to the engine as `Prompt::Tokens`.
7. **`/apply-template`** renders the chat route's prompt (same message conversion and template) and returns `{"prompt"}`. The chat body parsing moves out of `chat_completions` so the chat route, `/apply-template` and `/v1/responses` share it.
8. **`/v1/responses`** converts the request to a chat body as llama-server's `server_chat_convert_responses_to_chatcmpl` does (input string or items, `instructions`, `max_output_tokens`, `reasoning.effort`, `text.format`, function tools) and answers in the Responses shape (`response` object, or the `response.*` event stream, no `[DONE]`). `previous_response_id`, `input_file` and image parts are 400; non-function tools are skipped as there.
9. **`/infill`** builds the FIM prompt of `format_prompt_infill` (repo-level `FIM_REP`/`FIM_SEP` extra chunks, prefix 3:1 suffix split of `n_batch` 2048, optional BOS) from `Engine::fim_tokens`; a model that lacks a FIM token gets 501 `Infill is not supported by this model: ...` with the missing tokens named. The tiny fixtures have none, so the conformance case compares that error path; the layout is covered by a gateway test with a fake engine that has FIM tokens.
10. **Metrics for the new routes (rule 6).** One counter `tetraeder.gateway.requests` (`{request}`) with `http.route` (the matched route, never the raw path) and `http.response.status_code`; a panel "Requests by route" and the alert `GatewayAuthFailures` (401 share) ship with it.
11. **Health while loading.** `tetraeder serve` binds its port after the engine loads, so `/health` never answers 503 there; the 503 body (`Loading model`) exists for an engine that reports `ready() == false` (the replanner while it switches).

## Consequences

- llama-server clients (the web UI, `curl`, editor plugins that call `/infill` or `/completion`) work against the gateway. Native fields beyond the sampling ones of groups A and B are rejected or ignored as `sampling.rs` already does.
- `generation_settings` of the native response is the server's defaults overlaid with the request's own values; fields the engine has no notion of carry llama-server's default values (documented in the matrix).
- Open: the `input_tokens` routes, `suffix` on `/v1/completions`, `/slots`, `/lora-adapters`, `--props`, and `/health` 503 during load (see 11).
