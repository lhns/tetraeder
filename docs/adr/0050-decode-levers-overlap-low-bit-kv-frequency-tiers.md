# 0050. Decode levers: miss reads under CPU expert work, low-bit KV per attention unit, RAM tier by routing frequency

Status: Proposed (Phase 2 follow-up). (a) stage 1 superseded by ADR 0054 (I/O service, experts computed in arrival order); stage 2 keeps its gate on that path. Extends ADR 0035 (groups), 0038 (prefetch, "Reads that hide" item 4), 0031 and 0027 (KV in the plan). Does not change the prefetch levers of ADR 0038 (depth 2, reader 1 MiB at QD16, reads before the layer's own misses), which are implemented and measured first.

## Context

Exit regime (ADR 0045 addendum, box C, 26-core quota): Qwen3-235B-A22B Q4_K_M, RTX 3090, 91.4 GB RAM, 32K prefill, 10 VRAM slots per layer (10.97 GB), 77 RAM slots per layer. Decode 3.77 tok/s against KTransformers' 5.04. Per token 257 ms: compute 112, streamer 128. The streamer reads 511 MB per token: 414 MB by the prefetch reader (3.2 GB/s, 28% hidden) and 97 MB synchronously (5.2 GB/s, about 19 ms). RAM tier hit rate 93.2%, so one point of hit rate is about 75 MB, or 14 ms per token when the read is not hidden. Levers 1 to 3 of ADR 0038 are expected to bring the step to 150 to 170 ms. This ADR designs the next three, each sized against those numbers. The bar moves too: llama.cpp's expert cache with a CPU share of misses (ggml-org/llama.cpp#30966) is the new baseline (ADR 0045 addendum).

### (a) Is the layer's work overlapped today? No, it is serial.

For one MoE layer at decode under `MissPolicy::Cpu` the host runs, in order, on one thread:

1. Segment L computes attention and router and blocks: `sched.compute` (`crates/model/src/qwen3moe.rs:963`) wraps `ggml_backend_sched_graph_compute` (`crates/ggml-sys/src/ggml/sched.rs:121`), which synchronizes.
2. The host reads the ids, plans, starts the prefetch for later layers (`qwen3moe.rs:1009-1012`), then reads this layer's RAM misses synchronously: `stage_ram` (`qwen3moe.rs:1023`) runs `fill_ram`, which calls `read_batch_with` on the main thread (`crates/model/src/experts.rs:766`, `:983`). Nothing computes meanwhile.
3. Segment L+1 then holds the CPU group and the VRAM group, CPU first: RAM groups are pushed to `pending` before the compute group (`qwen3moe.rs:1026-1047`), and `build_segment` chains them through `acc` (`qwen3moe.rs:1502-1507`), so the VRAM group's `set_rows` depends on the CPU group's.
4. Even without that dependency ggml would not overlap them. The scheduler is created with `parallel = false` (`sched.rs:36`), so it has no events (`vendor/llama.cpp/ggml/src/ggml-backend.cpp:2006-2010`); splits run strictly in order (`:1871`); a split whose input lives on another backend synchronizes that backend before copying (`:1854-1855`), and a split without inputs synchronizes the previous backend (`:1878-1884`). The CPU backend's compute is synchronous on the calling thread.

Only the prefetch reads for layers L+1 and L+2 run concurrently (the reader thread, ADR 0038). The GPU expert group, the CPU expert group and this layer's own miss reads are serial.

What overlap can buy is small on the GPU side: with 10 of 128 experts in VRAM, the VRAM group is one to three experts per token (tens of microseconds per layer), and attention L+1 depends on the CPU group of L. The independent work inside a layer window is the synchronous miss read (about 19 ms per token) against the CPU compute of the experts that are RAM hits (about 100 ms per token, 1.1 ms per layer). So this lever is mostly "reads under CPU work", not "GPU under CPU work", and it is not the main part of the KTransformers gap (that gap is read bytes and how much of them hide, ADR 0045 addendum).

### (b) Low-bit KV

The builder's KV cache is F16 (`alloc_kv`, `qwen3moe.rs:1434`), and the attention views assume two bytes per element (`qwen3moe.rs:1664-1665`). The plan IR carries KV only as bytes per device (`Stage.kv`, `crates/plan/src/plan.rs:131`); `ModelDesc.kv_bytes_per_token_per_layer` (`crates/plan/src/model.rs:89`) and the planner's layout (`crates/planner/src/layout.rs:143`) assume F16.

At the exit regime: 94 layers x 2048 B per token and layer x 33024 padded positions = 6.36 GB of F16 KV. Q8_0 K and V take 3.38 GB (frees 2.98 GB), Q8_0 K with Q4_0 V take 2.58 GB (frees 3.78 GB). One VRAM slot row is 1.10 GB (10.97 GB / 10), so the freed bytes buy 2 or 3 more VRAM slots per layer: 10 to 12 or 13 of 128.

ggml support at the pin: CPU flash attention takes quantized K and V. CUDA compiles `q4_0-q4_0`, `q8_0-q8_0`, `f16-f16`, `bf16-bf16` by default (`vendor/llama.cpp/ggml/CMakeLists.txt:208`); `q8_0-q4_0` needs `GGML_CUDA_FA_QUANTS` set at build time, a CMake define in `crates/ggml-sys/build.rs`, not a ggml change (Rule 8 does not apply). On Ampere a quantized KV takes the vector kernel only for one query row (`ggml-cuda/fattn.cu:648-657`); prefill and multi-token verify steps take the MMA kernel, which first converts the whole K and V of the layer to F16 (`fattn.cu:737-741`): a temporary of about 34 MB per tensor at 32K, and conversion work in every layer of every such step.

### (c) Fast tiers by routing frequency

The VRAM tier already pins the most routed experts (`refresh_hot_set`, `experts.rs:843`, ADR 0035). The RAM tier is plain LRU, and prefetch borrows its pin set for reads in flight (`experts.rs:555-556`, reset at `:673`). ADR 0038 item 4 asks whether keeping the most routed experts in the RAM tier cuts misses. The builder can record routing (`LoadOptions::record_routing`, `take_routing_log`, `RoutingStep` in `experts.rs:105`), but only in memory: no harness writes it, and it lacks the predictions, without which a replay mis-scores LRU (prefetched experts take LRU slots and are pinned while in flight).

## Decision

### (a) Miss reads under the CPU hit group; GPU group asynchronous only if measured worth it

- **Scope.** `MissPolicy::Cpu` with a RAM tier, steps that run without op offload (`n < op_offload_min_tokens`, ADR 0044: decode and verify steps), one CPU chunk (CPU experts at most the RAM slot count). Other steps take today's path. Behind `LoadOptions::overlap` (default off until a paired run shows a gain, then on).
- **Stage 1, reads under hits.** After `plan_cpu` and `prefetch_ahead` (unchanged, same place), the layer's CPU experts are split into RAM hits and RAM misses. The misses get their RAM slots (routed lookups, the counters `fill_ram` keeps today), are pinned with the hits, and are read by a second `memory::reader::Reader`, the urgent reader, on the main thread's direct files (the main thread does no synchronous read while it is in flight, so the bounce buffers are not shared). Meanwhile the host computes the hit group as a graph of its own on a CPU-only scheduler (`Sched::new(&[cpu])`), then waits for the misses and computes the miss group the same way. Both write their unweighted outputs into a host tensor `cpu_out_host` `[n_embd, n_pairs]`; one `set_bytes` copies it into a primary-backend state tensor `cpu_out`. Segment L+1 starts with `acc = set_rows(acc, cpu_out[:, 0..p], pairs)`, then the VRAM group and the weighted sum as today. The gathered input comes from `xn_host`, a host copy of `xn` read back with the ids (16 KB at decode).
- **Exactness.** Groups are per expert, so each expert keeps all its rows and the CPU kernel choice (ADR 0035); the input bytes are the same f32; the merge is a copy. Logits are bitwise equal with `overlap` on and off, on CPU and on GPU builds.
- **Safety.** The urgent reader writes only the miss slots, which are pinned and which the hit group does not read; the RAM tier outlives both readers (same ordering as ADR 0038). `settle` also waits for the urgent reader. No new `unsafe`: the reader's sink already exists in `memory`.
- **Stage 2, GPU group asynchronous (designed, built only on evidence).** The VRAM group runs as its own graph on a third scheduler, launched with `ggml_backend_sched_graph_compute_async` (new `Sched::compute_async` and `Sched::synchronize` in `ggml-sys`), before the hit group; the scheduler must report one split for it, else the layer falls back to stage 1. The host synchronizes before the next segment allocates. Build stage 2 only if stage 1's profiling run shows the VRAM group costing at least 5 ms per decode token (2% of the step), measured by running it as a standalone synchronous graph (`TETRAEDER_EXIT_TIME_GPU_GROUP=1`). Expected: below that, because the group is one to three experts.
- **What proves it (per-layer critical path).** Per layer step the host times `segment` (graph compute), `cpu_hits`, `read_wait` (waiting for the urgent ticket after the hit group), `cpu_misses` and `copy`. The read is hidden by `1 - read_wait / read_time` (`read_time` is the ticket's own duration). Proof: the hidden share at least 0.5 in decode on the exit regime, and the paired decode step shorter by at least the hidden read time minus the extra graph overhead, outside the noise band.
- **Metrics (Rule 6).** `tetraeder.moe.layer.duration` (histogram, s) by new key `tetraeder.part` (segment, cpu_hits, read_wait, cpu_misses, copy, gpu_group); `tetraeder.moe.read.hidden` (histogram, ratio, per layer step with misses). `StepProfile` gains `cpu_hits`, `read_wait`, `cpu_misses`; the exit JSON reports them. Panel "MoE layer critical path" (stacked parts per token, hidden share p50). Alert `TetraederMissReadsNotHidden`: overlap on, hidden share p50 below 0.3 for 15 minutes while misses occur (the reader is starved by the CPU quota: lower `prefetch_threads`).
- **Expected gain.** The 97 MB synchronous misses (about 19 ms per token on box C, plus their bounce copy) hide behind about 100 ms of hit compute, minus the extra graphs: about 1.4 more per layer (the hit graph always, the miss graph in the 38% of layer steps that miss, `1 - 0.932^6.5`), at 20 to 40 us each on a CPU-only scheduler, 3 to 5 ms per token. Net about 12 to 16 ms per token: 5 to 6% of 257 ms, 8 to 10% of a 160 ms step after the ADR 0038 levers. Stage 2: at most 2 to 4 ms.

### (b) KV format per attention unit

- **Plan IR.** `Assign` gains `kv_format: Option<KvFormat>`, `KvFormat { k: Format, v: Format }`, valid on rules that select attention units; absent means F16/F16, so existing plans stay valid. Allowed pairs: F16/F16, BF16/BF16, Q8_0/Q8_0, Q8_0/Q4_0, Q4_0/Q4_0 (the CUDA kernels compiled). `Plan::kv_formats(desc, replica) -> BTreeMap<u32, KvFormat>` per layer, like `unit_formats`. `ModelDesc::kv_bytes_per_token_per_layer_as(KvFormat)`: the existing field stays F16 bytes, so `n_embd_kv = field / 4` and bytes are `k.bytes(n_embd_kv) + v.bytes(n_embd_kv)`. Validator: `Issue::KvFormat { at, rule, detail }` for a pair outside the set or a rule without attention units. The stage's KV bytes stay a budget; the format sets how many tokens it holds (`Plan::kv_tokens`).
- **VRAM budget (ADR 0031).** KV is still never borrowed. The freed bytes go to VRAM slots, which are sized as today from a byte budget (`expert_slot_bytes`, ADR 0037): the planner's footprint (`crates/planner/src/candidate.rs:176`) takes the KV format, so a builder candidate with Q8_0 KV fits more slots in the same card. The flash-attention F16 temporaries of prefill (about 70 MB at 32K) count in the workspace.
- **Builder.** `LoadOptions::kv: KvFormat` (default F16/F16; the builder takes one format for every layer and refuses a plan with per-layer formats). `alloc_kv` allocates by type; the views use `ggml_row_size(type, head_dim)` for the head stride and the cache row size for the position stride; `set_rows` writes quantized rows (CPU and CUDA support Q8_0 and Q4_0 destinations). `kv_snapshot`/`kv_restore` already work in row bytes; the prefix cache (ADR 0049) gets the KV format in its entry key. `ggml-sys/build.rs` sets `GGML_CUDA_FA_QUANTS` to the default list plus `q8_0-q4_0`. libllama's `ContextParams` gains `type_k`/`type_v`, so the parity reference runs the same KV format.
- **Parity (Rule 2).** Per KV format, builder against libllama with the same `type_k`/`type_v`: greedy tokens equal and logits within the tolerance of `tests/parity.rs`, on CPU and on the GPU box.
- **Quality acceptance.** Mean KL(p_F16KV || p_quantKV) over the full vocabulary, builder logits, on Qwen3-30B-A3B Q4_K_M: the frozen exit prompt (`bench/prompts/exit_prompt.txt`) at 8K and 32K scoring the last 1024 positions, and the calibration text of ADR 0048 at ctx 512 (16 chunks). Bounds, anchored to the measured Q8_0-weights cost of 0.002979 nats (`bench/quality/qwen3-30b-bf16.quality.json`): Q8_0/Q8_0 mean KL at most 0.003 and top-1 agreement at least 0.99; Q8_0/Q4_0 mean KL at most 0.015 and top-1 at least 0.97, at every depth. A format that fails is not allowed in plans for that model. On the 235B the 64 greedy tokens are compared and reported.
- **Metrics (Rule 6).** `tetraeder.memory.capacity` and `.used` with `kind = kv` gain `tetraeder.format` (e.g. `q8_0/q4_0`); new gauges `tetraeder.kv.tokens` (cached) and `tetraeder.kv.capacity` (tokens the cache holds). Panel "KV cache: bytes by format, tokens used of capacity". Alert `TetraederKvNearFull`: cached tokens above 95% of capacity for 10 minutes (requests are about to fail with "context full").
- **Expected gain.** Decode: GPU attention reads 6.36 GB of KV per token at 32K, about 7 to 10 ms on the RTX 3090; Q8_0 halves that (3 to 5 ms saved), Q8_0/Q4_0 saves 4 to 6 ms. Two or three more VRAM slots move about 2 to 3% of the routed pairs from the CPU to the GPU, about 3 ms of CPU expert compute. Together about 6 to 9 ms per token, 3% of 257 ms, 4 to 5% of a 160 ms step. Prefill may lose a little (F16 conversion per layer); acceptance: prefill no more than 5% slower, paired. The larger value is outside decode speed: room for the draft model of ADR 0043 and contexts beyond 32K. The replay of (c) prices the slot part offline (VRAM 10 against 12 and 13) before the box run.
- **Speculative verify.** Verify steps have several query rows, so on Ampere they take the converting MMA path in every layer. Speculation keeps F16 KV until a paired run says otherwise.

### (c) Replay first, then the policy

- **Recorder.** `RoutingStep` gains `n_tokens`, `predicted` and `predicted2` (`Option<Vec<i32>>`, the readbacks the run loop already does with prefetch on). `exit_regime` writes a trace when `TETRAEDER_EXIT_ROUTING_OUT` is set, draining `take_routing_log` after every `eval`. Format `tetraeder-routing` v1, in `crates/memory/src/replay/trace.rs`: one JSON header line (model, `n_layer`, `n_expert`, `n_used`, `id_bytes`, VRAM and RAM slots, prefetch depth, hot-set source, ubatch, prompt hash), then binary little-endian records: kind (`u8`: 0 layer step, 1 hot-set refresh), step (`u32`), layer (`u16`), `n_tokens` (`u32`), flags (`u8`: predicted, predicted2), ids, then the predictions (`u8` per id when `n_expert <= 256`, else `u16`). About 25 MB for the 235B at 32K plus decode, 75 MB with predictions. Traces stay on the box and in the fetch; the scores are committed.
- **Replay scorer.** `crates/memory/src/replay/` drives the real `SlotCache` per tier. Per layer step it makes the engine's calls in the engine's order (wait for the layer's prefetch, VRAM lookups, prefetch top-up and next reads from the recorded predictions, RAM lookups hits first). To keep that order identical the prefetch selection in `Streamer::start_prefetch` (votes, skip VRAM-resident, resident versus missing, budget) moves to a pure function in `memory` that both use. The VRAM hot set comes from counts at the recorded refresh. Policies for the RAM tier: `lru` (as built), `freq:P` for P in 0.25, 0.5, 0.75, 1.0 (the top `P x slots` experts by routing count so far are pinned, refreshed every 16 decode steps and at each recorded refresh; the rest LRU), and `belady` without prefetch (an upper bound). Output per (VRAM slots, RAM slots, policy, prefetch replayed or not): RAM hit rate, disk bytes per decode token, synchronous miss bytes per decode token, prefetch reads wasted. Run as `tetraeder-bench replay --trace F --vram 10,12,13 --ram 48,64,77,96,110 --out bench/results/<date>/replay-*.json`.
- **Fidelity gate.** Replaying `lru` with the run's own configuration must give the run's measured decode RAM hit rate within 0.5 points; otherwise the replay is wrong and decides nothing.
- **Decision threshold.** Build the tier policy only if, on a 235B text trace (frozen prompt, 32K, 256 decode tokens), with prefetch replayed, at VRAM 10 and RAM 77 and at the RAM count of a 128 GB box (about 100), the best `freq:P` cuts disk bytes per decode token by at least 10% against `lru` without raising synchronous miss bytes. 10% is about 51 MB, about 10 ms per token when not hidden, 4% of the step, above the noise band. If `belady` is within 10% of `lru`, stop: no online policy can pass.
- **The policy, if built.** `LayerSlots` keeps two pin sets: frequency pins (`set_frequency_pins`, new) and transient pins (`set_hot_set`, as today for prefetch). Eviction skips both; `pinned_count` is their union and never exceeds the active slots; the prefetch budget is `slots - union`. `Streamer` refreshes the frequency pins from `counts` with the winning P (`LoadOptions::ram_pin_share`, default 0 = LRU) at the same points as the VRAM hot set. Metrics: `tetraeder.expert.pinned` (gauge by tier and source: frequency, prefetch); panel "RAM tier: hit rate and pinned slots"; alert `TetraederRamTierHitDrop` (RAM-tier hit ratio more than 5 points below its 24 h mean for 30 minutes: routing has drifted from the pinned set, refresh the profile).
- **Expected gain.** Unknown until the replay; the threshold above is the gain that pays. The trace also prices (b): the VRAM 12 and 13 rows give the share of pairs that leave the CPU.

## Consequences

- None of the three closes the 1.34x gap alone (257 to 191 ms needs 66 ms). Their sum, 25 to 35 ms, matters if ADR 0038's levers 1 to 3 land near 170 ms rather than 150; they are ranked (a), (c) if the replay passes, (b) for decode speed, and (b) first for draft-model room.
- (a) adds 1.4 graphs per layer step and a second reader thread; under a tight CPU quota the urgent reader competes with ggml's spinning threads as the prefetch reader does (ADR 0038). The alert catches it.
- (b) touches the plan IR (a new optional field) and the planner's footprint; the planner does not enumerate KV formats until the quality numbers exist per model. The `bench/quality` profiles gain no KV entries in this ADR.
- (c) adds a binary trace format owned by `memory`; `tetraeder-bench` gains a dependency on `tetraeder-memory` without default features (no ggml build when built alone; in a workspace build feature unification links ggml anyway).
- All box measurements wait for the hold on box runs to lift; local tests use the synthetic MoE of `tests/common/synth.rs`.
- Implementation briefs: `docs/levers-briefs.md`.


## Implementation notes

### (c) first half: recorder and replay (Brief C1, branch `track-i-routing-replay`)

Built: the recorder, the trace format, the replay scorer and `tetraeder-bench replay`. No engine behavior changed; no runtime metric (bench tooling, results are JSON).

- `RoutingStep` gained `n_tokens`, `predicted`, `predicted2` and `refresh: bool`. The run loop fills the predictions from the readbacks it already does (this layer's `pred` for layer + 1 and `pred2` for layer + 2, the same values `prefetch_ahead` uses). A hot-set refresh pushes a marker (`refresh = true`, empty ids). The resident whole-step path sets the predictions to `None`.
- `memory::replay::trace`: `tetraeder-routing` v1 as in (c), plus `expert_bytes` per layer and an optional `profile` in the header. A truncated file is an error.
- `memory::replay::prefetch_plan` is the selection of `Streamer::start_prefetch`, now shared; `tests/prefetch.rs` is unchanged and green.
- `memory::replay::sim` drives the real `SlotCache` for both tiers in the engine's call order, including the refresh through the RAM tier. Policies `lru`, `freq:P`, `belady`. `memory` gained `serde` and `serde_json`.
- Harness: `TETRAEDER_EXIT_ROUTING_OUT` in `exit_regime.rs` (`tests/common/trace.rs`). Box stage: `trace` in `scripts/exit_run.sh`, called by `scripts/exit_session.sh` (written, not run: box runs are on hold).
- Fidelity (`crates/model/tests/replay_fidelity.rs`, label `cpu`): per layer, the replay's RAM hits and misses equal `ExpertStats` exactly, as do the prefetch issued, used and wasted counts and the decode hit rate, for depth 1, depth 2 and prefetch off. On the synthetic exit regime (8 layers, 16 experts, 2 VRAM and 4 RAM slots, 128 prompt tokens, 48 decode tokens) the replay gives the harness's decode `ram_hit_rate_mean` 0.3452 against 0.3452 measured and the decode disk bytes per token 88515072 against 88515072. Result: `bench/results/20261109-local/replay-synthetic.json`.

Deviations and choices:

- Depth-2 prefetch uses the prediction made at layer L for layer L + 2 in the same layer step, as `prefetch_ahead` does (`predicted2[seg + 2]` is set at `seg`). The brief said "recorded two layers back"; the code and the replay agree, the brief was loose.
- `freq:P` pins the top experts by routing count so far leaving out the experts pinned in the VRAM tier: those never reach the RAM tier, so counting them would waste pins. Pins that are not resident yet are not prefetched; they protect an expert once it is loaded. Frequency pins count against the prefetch budget (they are passed to `prefetch_plan` like reads in flight). With `freq:1` every slot can be pinned and a miss is read without being cached (bypass), so it can beat `belady`, which always caches the missed expert. The stop rule "belady within 10% of lru" therefore reads `belady` as the always-caching optimum, not as a bound on every policy.
- The refresh's RAM lookups and reads count in the phase of the step before the marker (prefill). `ram_hit_rate` counts the routed and refresh lookups; `ram_hit_rate_engine_mean` also counts the prefetch's own lookups as misses, which is what the harness reports and what the 0.5-point gate compares.
- `belady` first replays `lru` without prefetch to learn when each expert is looked up (that set does not depend on the RAM policy), then evicts the expert used farthest ahead; it runs without prefetch.
- The box stage uses the ADR 0038 levers (prefetch on, depth 2) rather than `main` (prefetch off): a trace without prefetch has no predictions to replay.
- `memory` had no `Win32_Security` feature on `windows-sys`, so `--no-default-features` (which the bench dependency uses) did not compile on Windows by itself; added.
- Local `cargo build --workspace` needs `vendor/llama.cpp`; a fresh worktree has it empty, so the local runs used a copy of the main checkout's.

Open: the replay on the 235B trace (decision threshold of (c)) waits for the box. C2 stays gated on it.

### (b) low-bit KV (Brief B, branch `track-j-lowbit-kv`)

Built from `docs/levers-briefs.md` Brief B. Decisions held; local checks only (CPU, synthetic model); the GPU parity and the KL acceptance wait for the box.

- **Plan IR.** `KvFormat` (`crates/plan/src/kv.rs`), `Assign.kv_format`, `Plan::kv_formats`, `Plan::kv_tokens`, `ModelDesc::kv_bytes_per_token_per_layer_as`, `Issue::KvFormat`. `kv_tokens` divides the budget of a device by the stage's per-token bytes and assumes the devices that hold a budget share each layer's KV evenly. The property test `kv_tokens_fit_the_budget` covers memory never exceeded and the 1.88x Q8_0 gain.
- **Planner.** `footprint` and `build_plan` take a `KvFormat`; `feasible_vram_tiers_kv` is the format-aware tier list (the old name keeps F16). Enumeration is unchanged. Related fix in a separate commit: `vram_slot_bytes` no longer adds ADR 0034's `n_used` parking rows (ADR 0035 removed them). The `n_used` f32 accumulator in `footprint` stays, because ADR 0035's pair groups write one.
- **Builder.** `LoadOptions::kv`; K and V caches are allocated by type, views use the cache's own strides (V and K may differ in type), a pair outside `ALLOWED` or a head size that is not a block multiple is a load error. Per-layer formats are not representable in `LoadOptions`. `MemoryUse.format` carries the KV format; `finish_step` sets `tetraeder.kv.tokens` and `tetraeder.kv.capacity` and the `tetraeder.format` attribute on the `kv` memory gauges.
- **Prefix cache.** Entries are keyed by the KV format (`Backend::kv_format`); a snapshot of one format is never restored into another.
- **ggml-sys.** `GGML_CUDA_FA_QUANTS` adds `q8_0-q4_0` to the default list when CUDA is on; `ContextParams` has `type_k` and `type_v`.
- **Harness.** `TETRAEDER_EXIT_KV` (both engines, recorded in the JSON `options.kv`). Box stages `kv-q8`, `kv-q8-slots`, `kv-q8q4`, `kv-q8q4-slots` in `scripts/exit_run.sh` (listed in `scripts/exit_session.sh`) and `kv-quality` (test `crates/model/tests/kv_quality.rs`, ignored). Not run.
- **Deviation: libllama rotates a quantized cache.** At the pin, libllama applies a Hadamard rotation to K, V and Q whenever `type_k` or `type_v` is quantized and the head size is a multiple of 64 (`llama-kv-cache.cpp`, `LLAMA_ATTN_ROT_DISABLE`). The builder stores plain values, so with default settings its logits do not match libllama's (synthetic model, head size 64: 0.19 on a logit of 25 at position 0, Q4_K_M weights). Parity therefore runs the reference with the rotation off (`llama::disable_attn_rot()`, an environment variable, because `llama_model_set_attn_rot` has C++ linkage; on Windows it also needs `_putenv_s`); with it off the deltas are exactly 0 for all three formats, resident and streamed. The exit harness reference does the same unless `TETRAEDER_EXIT_REF_ATTN_ROT=1`. Consequences to settle on the box: (1) llama.cpp's quantized KV is better than the builder's at equal bits, so a speed pair against `llama-bench -ctk q8_0` compares different quality; (2) the KL bounds above are for the plain cache and may fail for Q8_0/Q4_0; if they do, the follow-up is the same rotation in the builder (a Hadamard rotation of Q, K, V and the attention output, as libllama does), not a looser bound.
- **Local KL (informative).** Synthetic random-weight model (head size 64, Q8_0 weights), 2K context, last 256 positions, builder against its own F16 cache: Q8_0/Q8_0 mean KL 0.119 and top-1 0.906; Q8_0/Q4_0 1.172 and 0.648; Q4_0/Q4_0 1.721 and 0.574. Random weights give flat, outlier-heavy attention, so these say nothing about Qwen3; the acceptance is `kv_quality.rs` on the box.
- **Tests.** `crates/plan/tests/kv.rs`, `props.rs`, `crates/planner/src/builder.rs`, `crates/model/tests/kv_format.rs` (parity against libllama with the same `type_k`/`type_v`, resident and streamed, snapshot roundtrip, memory report, refusals, KL at 2K), `crates/scheduler/src/prefix_cache.rs`. ## Addendum 2026-11-09: Hadamard rotation of a quantized KV cache in the builder (branch `track-s-kv-rotation`)

**Decision.** The builder rotates Q, K and V like libllama does, so a quantized-KV builder matches libllama with its default settings and a speed pair against `llama-bench -ctk q8_0` compares equal quality. This settles consequence (1) of the deviation note above; the "follow-up" in (2) is this change.

- `LoadOptions::kv_rotation: Option<bool>`: `None` rotates exactly when the K (V) type is quantized and the head size is a multiple of 64, as libllama (off for F16). `Some(true)` forces both sides (error if the head size is not a multiple of 64), `Some(false)` turns both off. `Qwen3Moe::kv_rotated()` reports the result.
- Same construction as libllama, no new transform: the orthonormal Walsh-Hadamard matrix of `ggml_gen_hadamard` (`llama-kv-cache.cpp:21-54`, `ggml_sys::ggml::hadamard_matrix`); K matrix side = largest power of two dividing the head size, at least 64, V side 64 (`:329-345`); Q and K multiplied by the K matrix after RoPE, V by the V matrix before the cache write, the attention output by the V matrix again (the matrix is its own inverse) before `wo` (`llama-graph.cpp:3246-3253`, `:3291-3293`); each as `llama_mul_mat_hadamard` (`llama-impl.h:57-75`: reshape to `[n, rows]`, `mul_mat`, hint `GGML_HINT_SRC0_IS_HADAMARD`), here `Context::mul_mat_hadamard`. The hint matters: the CPU path then uses the FWHT kernel, so results match bit for bit.
- The matrices are F32 tensors in a context of their own (the KV buffer and the memory report stay exactly the cache).
- Exit harness: `TETRAEDER_EXIT_KV_ROT` (0/1) sets `kv_rotation`; the reference engine follows it (`TETRAEDER_EXIT_REF_ATTN_ROT` overrides the reference alone, so a pair that keeps llama.cpp's default needs no setting). The JSON options record `kv_rotation` as resolved. With `TETRAEDER_EXIT_KV_ROT=1` and `f16`, the builder rotates and libllama does not; do not pair that.

**Tests.** `crates/model/tests/kv_rotation.rs`: builder against libllama with its rotation on, Q8_0 synthetic model, resident and streamed, all three formats: max delta 0 (bitwise) on Windows locally; defaults and the head-size error. `kv_format.rs` keeps the rotation-off parity (`kv_rotation: Some(false)`, delta 0). libllama's switch is process-wide, so the two live in separate test binaries.

**Local KL (informative).** Synthetic random-weight model, head size 64, Q8_0 weights, 2K context, last 256 positions, against the unrotated F16 cache (`kv_format.rs::cpu_quantized_kv_kl_at_2k`):

| Q8_0/Q8_0 | 0.119 / 0.906 | 0.159 / 0.879 |

## Note 2026-11-10b: the KL floor, and gating on the cost above it (branch `track-ao-kvq-floor`)

**Second run** (`bench/results/20261110b/kv-quality.json`, box 60050186, A40). Mean KL against the builder F16 reference, 8K / 32K / calibration:

| row | mean KL | top-1 |
|---|---|---|
| builder F16, rotation off (the reference again) | 0 / 0 / 0 | 1 / 1 / 1 |
| builder F16, rotation on | 0.0093 / 0.0089 / 0.0068 | 0.960 / 0.955 / 0.963 |
| libllama F16 | 0.0079 / 0.0072 / 0.0077 | 0.958 / 0.960 / 0.968 |
| builder Q8_0/Q8_0, rotation on (gating) | 0.0107 / 0.0095 / 0.0075 | 0.958 / 0.963 / 0.968 |
| libllama Q8_0/Q8_0 | 0.0103 / 0.0094 / 0.0076 | 0.956 / 0.958 / 0.968 |
| builder Q8_0/Q4_0, rotation on (gating) | 0.0169 / 0.0145 / 0.0145 | 0.933 / 0.946 / 0.953 |

**Cause, measured.** Not a rotation bug: a wrong inverse, a one-sided rotation or a wrong scale changes attention scores outright (KL far above 1), and an overflow gives NaN; the rotated builder matches libllama bit for bit on the CPU (`kv_rotation.rs`), on CUDA both take the FWHT kernel (its dispatch conditions hold for these shapes, `fwht.cu`), and builder and libllama Q8_0/Q8_0 land at the same KL. Not run-to-run noise: the reference against itself is exactly 0. And the cost does not scale with the size of the perturbation: F16 rounding of rotated values, another engine's kernels and Q8_0 rounding (about 16 times coarser) all cost 0.007 to 0.011, where smooth error would scale with its square. So the bounds of 0.003 and 0.99 lie below what F16 itself scores.

**Cause, hypothesis (not measured).** Discontinuities saturate the cost: every quantized-weight matmul on CUDA quantizes its activations to Q8_1 (MMQ, `mmq.cu`), so an ulp change flips 8-bit rounding decisions, and the router picks 8 of 128 experts in each of 48 layers, so flipped choices reach every later position through the cache. Unexplained: the Q8_0-weights anchor (0.002979, `llama-perplexity --kl-divergence` against BF16 logits, ADR 0048) is a much larger perturbation that scores below this floor on the same calibration text. The same-engine rows below test this: under saturation libllama Q8_0 against libllama F16 lands near the floor too; if it lands near 0, the builder is the outlier and this diagnosis is wrong.

**Decision.** Gate on the cost above the floor, paired by position. The floor row is the builder's F16 cache with the rotation forced on: same engine, same batching, same rotation as the gating rows, so the KV format is the only difference. Per set, excess = mean over positions of KL(gating row) minus KL(floor row), both against the reference, with its standard error; excess top-1 loss = floor top-1 minus gating top-1. Bounds, provisional until a run has the new floor rows: Q8_0/Q8_0 excess KL at most 0.003 and excess top-1 loss at most 0.01; Q8_0/Q4_0 at most 0.015 and 0.03 (the ADR's numbers, read as cost above the floor). A row whose bound lies within two standard errors of its excess is flagged `marginal`. The absolute bounds stay in the JSON (`abs_pass`), not gated. On 20261110b the excess would be 0.0014 / 0.0006 / 0.0007 (Q8_0/Q8_0) and 0.0076 / 0.0056 / 0.0077 (Q8_0/Q4_0); those numbers are not why the bounds are what they are.

**Diagnostic rows added.** The reference in ubatches of 128 (below the 256 scored positions of a calibration chunk, so the chunking of every prefix and scored tail changes): whether batching alone moves it to the floor; exactly 0 means the builder is batch independent. Each engine's formats against that engine's own F16 row (builder Q8_0 against builder F16 rotated, libllama Q8_0 against libllama F16): whether libllama sees the same floor against itself. `kv_format.rs::cpu_quantized_kv_kl_at_2k` now also prints F16 rotated against F16 on the synthetic CPU model.

**Consequence.** One more builder run (a minute or two on the A40, the small ubatch is slower); peak host memory is the reference, one baseline and the current row (about 11 GB). The floor varies by about 0.0015 between perturbations (builder rotated against libllama F16 above), half the Q8_0/Q8_0 bound. The standard error treats positions as independent, but positions in one sequence share the perturbation through the cache, so it is a lower bound and `marginal` is optimistic. If the rerun shows marginal rows, the next step is more scored positions or more floor samples, not looser bounds.

## Addendum 2026-11-12: an adaptive VRAM tier in the replay (branch `track-vram-policy-replay`)

Question (section c): on the 235B the llama.cpp expert cache decodes 1.35x to 1.54x faster than the builder at the same VRAM budget (ADR 0045, results 20261112a). The builder's compute tier is a static hot set picked after the first prefill ubatch; every other expert runs on the CPU. The cache admits experts during decode. Would an adaptive VRAM tier raise the decode VRAM pair share (0.178 in `bench/results/20261110c/replay-235b.json`) enough to matter?

Decision: the replay gets a VRAM-tier policy, `Config::vram_policy`, grid flag `tetraeder-bench replay --vram-policy` (default `static`). No change to the engine's policy in this branch.

- `static`: as built; outcomes are unchanged and the JSON gains no fields.
- `prefill`: a static hot set from the routing counts of the whole prefill, taken when decode starts; the marker after the first ubatch is ignored.
- `lru` and `lru:<pin share>`: every decode miss is admitted after its step, evicting the least recently used unpinned expert. The marker loads the hot set; `pin` of the slots keep it pinned (`lru` pins none).
- `freq`: every `FREQ_REFRESH_STEPS` decode steps the per-layer top-N by routing counts is pinned again and newcomers are copied in.

Non-static outcomes add `vram_policy` and, per phase, `vram_admit_bytes_per_token` (bytes copied to VRAM by admissions, decode only). The replay models no RAM-tier traffic or time for admissions, so `--timed` ignores their cost; the byte count is the cost to compare against the share gained. The engine side reports the same share as `vram_pair_share` in the exit JSON (per decode window and per run): the exit-JSON view of the existing counter `tetraeder.expert.cache.requests` (compute-tier hits over hits plus `cpu` lookups, from `ExpertStats`), so it adds no metric, panel or alert. The exit JSON also splits `sched.compute` per decode token into segments with a RAM-tier group and those without (`seg_compute_cpu_ms`, `seg_compute_gpu_ms`) and gives the CPU pair count (`cpu_pairs`); these live in `StepProfile` only, because no `tetraeder.moe.layer.duration` part covers them.

The answer needs a real trace replayed at the 235B slot counts; this addendum adds the tooling only.

## Addendum 2026-11-12b: (c) built, off by default (branch `track-ram-freq-pin`)

`LoadOptions::ram_policy` (`lru`, the default, or `freq:<share>`; exit harness `TETRAEDER_EXIT_RAM_POLICY`, recorded in the options as `ram_policy`). It is for slow disks, where read waits dominate; on fast disks it changes no step time, so it stays off.

- Same semantics as the replay's `Policy::Freq`: in decode, the top `ceil(share * RAM slots)` experts of each layer by routing count, leaving out those pinned in the compute tier, are pinned in the RAM slot tables (`LayerSlots::set_hot_set`, no new structure). Refreshed at decode step 0, every `FREQ_REFRESH_STEPS` (16) decode steps and at each hot-set refresh. The rest of the tier stays LRU, and prefetch counts the pins as slots in use, like reads in flight.
- Two rules the engine needed, now in the replay too: the pins are held in decode steps only (a prefill step can route more distinct experts than the unpinned slots hold, and the engine cannot serve a miss without a slot), and pins give way, least routed first, when a layer step's chunk plus the pins would exceed the tier (`pins_with_room`). The replay used to serve such a miss without caching it. The two agree wherever pins and a step's experts fit, which the fidelity test checks (`freq:0.5` at 20 and 24 slots of the synthetic model). At `freq:1` on a real tier the engine keeps `slots - the step's experts` pins, not all of them, so the replay number for `freq:1` is not what the engine does; confirm with `freq:0.5` to `0.75`.
- Results are unchanged: logits are bitwise those of LRU on the CPU backend, also under overlap and in tiers too small for the pins (`replay_fidelity.rs`). Pin invariants are property tests (`freq_pin_props.rs`).
- Metrics (rule 6): no new series. The effect shows in `tetraeder.expert.cache.requests` for tier `ram` (hit rate) and the disk read bytes already on the panel; no alert fits.
- To confirm on a slow disk: stage `main-overlap-ramfreq` (`TETRAEDER_EXIT_RAM_POLICY=freq:0.5`), paired with `main-overlap`, with repeats.
