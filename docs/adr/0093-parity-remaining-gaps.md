# 0093. The remaining llama-server parity gaps (node serving-parity-remaining)

Status: Accepted (advisor, delegated by the owner 2026-11-26). After M2, ADR 0083 decision 6. Matrix: [docs/notes/llamacpp-parity.md](../notes/llamacpp-parity.md). Supersedes ADR 0089 item 5 in one point: `/props` reports `endpoint_slots` true.

## Context

The audit of ADR 0083 decision 6 left six strict gap cases: `response_format`, forced `tool_choice`, `continue_final_message` with `add_generation_prompt` and `prefill_assistant`, the `input_tokens` routes, `GET /slots` and prompt arrays on `/v1/completions`. The target is llama-server at the pin (b12426). All changes are in the gateway; the engines, builders and kernels are untouched.

## Decision

1. **`input_tokens`.** `POST /v1/chat/completions/input_tokens`, `/chat/completions/input_tokens`, `/v1/responses/input_tokens` and `/responses/input_tokens` render and tokenize the body as its generation route would and answer `{input_tokens, object: "response.input_tokens"}`, as `handle_count_tokens` does.
2. **`GET /slots`.** One entry per slot with the fields llama-server always gives (`id`, `n_ctx`, `speculative` false, `is_processing`); `?fail_on_no_slot=1` is a 503 when no slot is idle. The gateway admits requests by count, not by slot id, so `is_processing` marks the first busy-count slots, not the slot a request really runs on, and the per-task fields (`id_task`, `params`, `next_token`, `prompt`, `generated`) are not given. `/props` reports `endpoint_slots` true. There is no `--no-slots` flag.
3. **Prompt arrays on `/v1/completions`.** As `tokenize_input_prompts`: an array with no number in it is a batch, anything else one prompt (token ids and mixed arrays are tokenized as on `/completion`). Choices are numbered prompt-major (the `n` choices of prompt 0, then of prompt 1), usage takes the first prompt's tokens and sums the completions, as llama-server merges its results. A batch whose choices fit the slots runs at once; a longer one runs one prompt after the other, each prompt's choices finished before the next is admitted (a queued prompt cannot wait on a slot whose output nobody reads). A streamed batch longer than the slots is refused with 400.
4. **Continuation on the OpenAI routes** (chat and responses). `continue_final_message` (true, `content`, `reasoning_content`) and `add_generation_prompt` follow `oaicompat_chat_params_parse`: a trailing assistant message is continued without a flag (`prefill_assistant` is on by default there and has no switch here), both flags true is a 400, two trailing assistant messages and a continued message with tool calls are 400s, with llama-server's texts. The prompt is built as `peg_generator::generate_parser` builds it: the conversation before the message, the template's generation prompt (on a thinking template cut before its `<think>`, which is reopened with the message's reasoning and closed for a content continuation), then the message's content. A whole reply starts with the continued text (llama-server parses the reply from the prefill on); streamed deltas do not repeat it. The Anthropic prefill keeps its own construction.
5. **`response_format` on chat.** Without tools, without a thinking template and without a request grammar, `json_object` and `json_schema` become the grammar llama-server builds for them (`chat-auto-parser-generator.cpp:119-124`, rendered by `common_peg_arena::build_grammar`): `space space ("```json" space S space "```" | space S space)`, where `S` is llama.cpp's converter output for the schema (the `json_schema` path of ADR 0088) and `space` the converter's rule. llama-server's grammar starts with the generation prompt, which its sampler is fed first; this one starts after it. The grammar is rebuilt in the gateway from the pinned source rather than by calling llama.cpp's chat parser, which would need the chat and PEG code in the ggml-sys shim; a pin move must recheck it (cases `response-format-*`). With tools or a thinking template the token mask (llguidance) stays: llama-server then builds one grammar for the think block, the tool calls and the payload. Where the schema comes from and its errors follow `oaicompat_chat_params_parse` (`json_object` takes `schema`, `json_schema` takes `json_schema.schema` or `schema`, an empty schema is any object).
6. **Forced `tool_choice` stays open.** On the fixture's chatml template, which renders no tools, llama-server builds no grammar and answers plain text for a forced choice; the mask here forces a call. Dropping the mask would break forced calls on real templates, so the case waits for a fixture template with tool calls.
7. **Metrics (rule 6).** The new routes are counted by `tetraeder.gateway.requests` per matched route and status, in the existing panel "Requests by route"; no new metric, panel or alert.

## Consequences

- A trailing assistant message on `/v1/chat/completions` and `/v1/responses` now continues that message instead of starting a new turn after it.
- `response_format` output on a model without tools or thinking is shaped by the grammar sampler, not the mask; constrained tokens at temperature 0 follow llama-server's.
- Open: forced `tool_choice`, `response_format` with tools or a thinking template, the reasoning controls (no thinking template in the fixture), real slot ids in `GET /slots`.
