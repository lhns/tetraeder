### Second cold request, most likely cause

Read from `split30/` (the committed admit lines and round files; the replica's own log at warn level was not kept). Every failed round shows one of two shapes. Run 3 r2: admitted at 14:02:38.0 after `place_ms=5211.60 save_ms=5045.66 attempts=2 saved=2:2177` (the eviction of r1's 2177-token idle sequence, saved through the remote segment over the WAN), ended 1.3 s later with `completion_tokens 0, cached_tokens 1`. Run 3 r3 and run 2 r1 to r3: no usage event, ended 5.4 to 5.6 s after submit (run 3 r3, run 2 r1), or sooner (run 2 r2 1.35 s, r3 0.15 s). One suspect fits both. The save took 5.05 s, the `RemoteConfig::deadline_floor` of every call is 5 s (`max(5 s, 10 x predicted decode step)`, and the prefill step and the snapshot got the same deadline as a decode step), and the a to b bulk path varied from 0.9 to 2.8 s per 4 MiB. A call past the deadline drops the connection to the segment worker (`recv_call`, `kill`), the backend then reports its sequences lost and fails the request. The failure is an error event on an open 200 stream, and `scripts/phase6_split_round.py` reads only `usage` and `choices` from the stream, so an error event shows as an empty stream with `error: null`. The CPU test passes because its snapshots and steps take milliseconds, and run 1's repeated prompt never evicted (it hit the idle sequence, `common=2047`).

Not confirmed. The replica's log for the window is not in the committed data: the leader was node b, whose `node.log` in `b-logs.tgz` ends at 13:32 UTC and whose `final/b` log starts at 14:07, while the split rounds ran 13:40 to 14:05. What the data of node a (`final/a/ff/node.log`, segment 0 to 48 of c01) adds: its worker built its snapshot buffer pool at 14:02:33.02, the moment the eviction save of run 3 began, which matches a snapshot request arriving there; no worker restarted in any run (one model load per head start), which is also what a killed connection looks like, since the leader closes the connection and the daemon keeps the worker. So the 5 s deadline is the leading suspect, not a finding. The fix is a hardening whatever the cause: `RemoteConfig::bulk_deadline` (120 s) for `seq_snapshot`, `seq_restore` and prefill steps (more than 64 tokens), and the CPU test `cpu_cold_prompts_that_do_not_fit_together_evict_the_idle_one_and_answer_like_one_node` (three prompts of about 2100 tokens in a 4096-row pool, so each evicts the one before, then two streamed with ignore_eos) now guards the eviction path on loopback. Unit tests with a scripted worker: `a_snapshot_over_a_slow_link_is_not_cut_at_the_floor` and `a_slow_prefill_step_gets_the_bulk_deadline_a_slow_decode_step_does_not` (`slowsnap:2000` and `slow:60` faults against a 1 s floor). A snapshot of 2177 tokens of the 30B's 47 layers is about 210 MB, so over the a to b path (1.5 to 4.4 MiB/s per 4 MiB frame in the probes) it can take far longer than 120 s: the cache save over a slow link may still be too slow to be worth it, and a box run should read `save_ms`. Added logging: `worker call failed, the worker is killed and starts again` (call, took_ms, deadline_ms) in the leader, and `request ended by length before its first token` in the scheduler. A box run settles it with: the leader's stderr at warn level kept for the whole session (`node.log` of node b), those two lines and `cannot save a sequence`, and `phase6_split_round.py` recording an `error` event of the stream (CI lane's script, read only here: it reads `usage` and `choices` only, so an error event shows as an empty stream). The node stays open until a box run shows the second cold request answering.

Reading. On fitted rates the 235B pick on rehearsal 2's link is link bound: pp is 81 tok/s, a prompt of 25 s, of which the a to b hop of the one 32 MiB frame (and the b to a return) is most, so each probe's bulk rate goes straight into pp. The gate's rule (pp and tg each move by at most 0.08 between two full probes 10 minutes apart) would have aborted the pair on rehearsal 2's link: pp moves 24% to 43% against the first probe (the five probes are not 10-minute pairs, but their spread is the same order as the 3.5 times the bulk rate varied between probes of that session). Rehearsal 1's link, like for like, would have passed (0.15%). Decode passes on both (under 3.5%). A Case S session needs a link whose bulk rate holds within a few percent between two probes; the gate finds out before the 142 GB download. Not a measurement: the node rates are one fit, the 32 MiB hop is extrapolated from the 4 MiB point on rehearsal 2's probes (rehearsal 1's reach 64 MiB), and the fit that the pick will be priced on comes from the anchors of this session, not from this one.
